# 第二次任务进阶档实现原理与录屏详解

2026年11月12日。依据当前源码、原始运行记录、工作台接口与公开一手资料整理。当前选题为第二次实践任务中的“Skill做多”，录屏按进阶档组织。

当前网页采用固定CourseDock测试用例。输入框替换自然语言request，facts和六项验收标准仍从原用例加载。修改同一完整材料任务的表述后可观察新编排，换成其他业务时需要同步配置该业务的事实与验收标准。模型会同时收到request和facts。

本地seed为采样随机种子，用于控制本地规划、业务生成和审查请求的随机性，有助于复现。DeepSeek配置将本地seed归为无值，本页云端请求未设置API随机seed。表单中的模型、规模与seed控制下一次提交，下面已经显示的结果由job_id绑定到原配置。

现有60%、20%、90%表示固定任务的完整任务已验证正确率。实际组合检查包括至少两种不同Skill和真实产物依赖，最终还需符合六项内容标准。具体Skill与子任务是否匹配，可结合原Skill说明、实际参数和结果核查。逐调用的工具选择命中率需要另行定义有效选择或参考标签并统计。

## 一、项目实现了什么

### 1. 从一个具体任务理解系统

输入要求为虚构开源项目CourseDock生成完整发布材料，包括功能与限制说明、两条给定命令的新手上手说明、实际空CSV反馈模板，以及标为建议的反馈流程和维护职责。

原始facts提供0.2.0版本、MIT许可、三项功能、三项限制、两条命令和四个反馈字段，同时把仓库地址、默认端口、服务地址、Web管理界面等保留为未知。完整输入与六项标准可在工作台点击“查看固定项目事实与六项标准”展开。

系统完成了以下业务流程。

1. 从真实来源Skill建立166项候选库，记录名称、原文、来源和摘要。
2. 规划模型接收完整需求、facts和候选接口，逐轮选择Skill及子任务。
3. 执行器读取被选Skill全文，连同facts和实际上游正文调用模型，生成材料。
4. 正文与CSV真实落盘，获得不可变DOC/FILE引用。
5. 模型通过这些引用继续组合Skill，审阅、修订并正式提交。
6. 系统保存实际调用、依赖、文件和检查结果，网页提供预览、下载与本人复核。
7. 对不同候选规模重复完整任务，报告最终内容复核后的正确率和失败原因。

已有网页成功实例为`3df8e6e13ec348f886e6889007ead0d4`，其实际业务链如下。

```text
完整需求 + facts + 166个候选Skill接口
    ↓
product-design-harness
    ↓ 产生 DOC-001、FILE-001-01
copy-editing
    ↓ 实际读取上述引用对应的正文和CSV
    ↓ 产生 DOC-002、FILE-002-01
审阅通过 → 正式提交 → 归档与本人复核
```

本轮候选N=166，实际Skill种数K=2，业务节点2，最长链2个节点。控制工具为`read_artifacts`、`review_deliverables`、`submit_deliverables`，166档共暴露169个工具。候选规模、实际种数、调用节点和链长各有独立含义。

### 2. Skill在这里如何执行

每个Skill注册为一个原生函数接口。规划器看到工具名称、原始说明和参数结构，其中`request`表达当前子任务，`artifact_ids`列出需要读取的已有产物。

模型选择`copy-editing`时，会返回类似下面的参数。

```json
{
  "request": "审阅并优化CourseDock发布材料，核对原始facts",
  "artifact_ids": ["DOC-001", "FILE-001-01"]
}
```

执行器依据名称找到原Skill，读取完整`SKILL.md`。业务模型实际收到原文、事实、子任务和上述引用对应的完整正文。随后模型返回材料，程序将返回正文原样保存，并导出其中的CSV附件。当前适配范围主要覆盖原文驱动的文本与文档能力，来源资格与原文身份都有记录。具体外部账号、服务或原作者脚本的执行能力需要各自的接入证据。

业务执行接口位于`experiments/skill_boundary_f/incremental.py`的`raw_worker`。规划、控制和交付逻辑位于`experiments/skill_boundary_f/progressive.py`的`make_tools`与`run_one`。

### 3. 编排为什么具有真实依赖

`ReferenceStore`为正文分配DOC引用，为附件分配FILE引用，保存生产节点、实际路径、完整内容及附件摘要。

下游提交`artifact_ids`后，执行器检查引用是否存在，找到对应文件和正文，再将内容交给业务模型。依赖边由引用对应的生产节点推导，节点深度按父节点最大深度加1计算。模型选择了哪种Skill、输入了什么引用、产生了什么文件，都能逐步追踪。

修订会创建新DOC/FILE引用。最终`manifest.json`明确列出交付对象，旧产物仍保存在证据中。规划器通常取得引用、长度和摘要等回执，需要全文时调用`read_artifacts`，下游业务执行和审查读取相关完整正文。

实现位于`experiments/skill_boundary_f/reference_store.py`与`planner_receipts.py`。

### 4. 规划循环与真实修正过程

运行器规定最多16轮规划，要求至少实际使用两种不同Skill，并形成至少一条服务于交付的真实产物依赖。具体工具、子任务和依赖由模型决定。

该网页成功实例的实际原生调用如下。

| 记录 | 实际动作 |
| --- | --- |
| `planner-00.native.json` | 调用`product-design-harness`生成初稿 |
| `planner-01.native.json` | 尝试提交，组合条件未满足，收到拒绝反馈 |
| `planner-02.native.json` | 调用`review_deliverables` |
| `planner-03.native.json` | 调用`copy-editing`，引用DOC-001和FILE-001-01 |
| `planner-04.native.json` | 审查修订后的交付集合 |
| `planner-05.native.json` | 调用`submit_deliverables`正式提交 |

`control-calls.json`保存了组合条件从未满足到满足的检查结果。全部六次规划、两次业务执行及两次模型审查共保存10条全新本地模型回复。首次失败与后续修正可以一同展示。

### 5. Airflow承担什么工作

网页创建统一`job_id`，保存需求和配置，再触发`skill_experiment`。Airflow调度结构如下。

```text
validate_request
    ↓
dispatch_to_host
    ↓
execute_skills
    ↓
verify_artifacts
    ↓
publish_results
```

| 任务 | 实际工作 |
| --- | --- |
| `validate_request` | 读取网页请求，校验规模、模型与参数 |
| `dispatch_to_host` | 写入Windows主机执行队列 |
| `execute_skills` | PythonSensor等待主机结果，使用reschedule释放Worker |
| `verify_artifacts` | 根据引用收集真实产物，核对正文及附件摘要，归档结果 |
| `publish_results` | 将结果标为可在工作台查看 |

Windows执行桥单并发领取队列任务，调用冻结F运行器和Ollama，保存原始证据。相同`job_id`贯穿网页、Airflow、主机目录和结果。Airflow图展示平台执行流程，工作台“实际Skill调用与依赖”展示模型生成的业务调用图。

DAG实现位于`airflow/dags/skill_experiment.py`，桥与执行入口位于`experiments/skill_portal/bridge.py`和`execute.py`。

### 6. 正确性与当前结果

一次完整任务要满足实际组合、正式提交、文件存在与一致性检查，并通过固定六项内容要求。程序检查命令、CSV、引用和摘要，模型审查语义，后续内容复核直接检查最终文件并绑定摘要。本人录屏时再按六标准核对。

| 六项标准 | 核查对象 |
| --- | --- |
| 功能、限制、版本和许可准确 | 0.2.0、MIT、三项功能与三项限制 |
| 两条上手命令准确 | 与原始quickstart逐字对应 |
| 实际空CSV正确 | 只有规定四列表头，字段顺序正确 |
| 未知保持未知 | 地址、默认值、界面等未给定信息 |
| 流程与职责可用且标为建议 | 建议范围、状态流转和责任角色 |
| 最终材料一致 | 正文、附件及多份文档之间一致 |

| 规模 | 完整任务次数 | 已验证正确 | 用途 |
| --- | ---: | ---: | --- |
| N5 | 3 | 1 | 小规模诊断 |
| N10 | 3 | 1 | 小规模诊断 |
| N40 | 3 | 1 | 小规模诊断 |
| N60 | 3 | 2 | 小规模诊断 |
| N80 | 3 | 0 | 小规模诊断，含一次未解决歧义 |
| 本地N100 | 10 | 6，60% | 正式十次统计 |
| 本地N166 | 10 | 2，20% | 正式十次统计 |
| DeepSeek N166 | 10 | 9，90% | 云端十次统计 |

本地为Qwen3.5:9b、32k、fact-evidence审查，云端返回名为deepseek-flash、legacy审查。各组使用相同内容验收标准，模型、上下文和自动审查配置存在差异。正确率以全部预定完整任务为分母，歧义保留在分母中。

## 二、制约继续增多的原因

### 1. 候选接口本身占用上下文

当前每轮规划同时暴露全部N个候选的名称、说明和函数参数结构。选中Skill后再加载其全文，这降低了预先加载所有全文的成本，但全部候选接口仍持续占用规划上下文。

166档网页实例的首次规划已有28781个prompt tokens，32k配置容量为32768，初次输入之后的余量约3987 tokens。后续回复、工具回执、审查反馈和状态继续增长，还需容纳生成内容。

可以用以下关系理解开销。

```text
请求占用 ≈ 系统说明 + 原始需求与facts + 候选接口 + 历史调用与反馈 + 当前状态
```

实际错误包括33582、33241、32849-token输入超出32768，32849-token同请求又两次复现超限。同一33582-token请求在40k可继续，后来41226-token请求又超出40960。现有证据定位到了请求容量限制。

### 2. 内容事实错误会在较小规模出现

本地100档seed10中，`service_url`为未知，材料进一步写成“无固定公网地址”。N10等小档也出现未知界面、安装与网络行为被补造的记录。工具可成功返回文件，内容仍需要逐项验证。

当前实际Skill适配以原文引导模型生成内容。原Skill中的作者信息、示例和通用写法可能被模型带入目标项目，后续Skill又可能沿用上游草稿中的错误。事实来源约束与真实内容审查用于发现和纠正这类问题。

候选相似性和长上下文中的信息利用困难可以作为后续验证的原因假设。已有记录尚未单独测量两者对错误率的贡献。长上下文使用能力需要独立评估，相关研究观察到信息位置会影响检索表现。[Lost in the Middle论文](https://arxiv.org/abs/2307.03172)

### 3. 修订会消耗轮数并增加历史

16轮是当前实验预算。读取、审阅、非法提交、修订及重审都会消耗规划轮次。N60/seed3曾生成新的正确CSV，但最终清单仍包含带旧错误CSV的文档，最终耗尽16轮。该次最大顶层请求约23576 tokens，记录显示其失败发生在修订与版本管理过程中。

因此，增加轮次会增加机会和资源开销，是否提升成功率仍要测量。关键约束包括选择有效动作、保留正确最终版本和及时完成交付。

### 4. 目前入口还固定了已验收库范围

当前注册表验收为166份不同原源，网页规模选项与配置校验为100和166。执行入口也核验原166份来源和冻结代码。后续更大规模需要加入新真实来源、完成能力资格检查，再以新版本扩展入口并测量。

166是当前最大已验证通过候选规模。已有不同N的正确率未形成单调变化，Skill数量的稳定临界区间仍待定位。

## 三、公开研究与工程资料中的解决方法

以下资料于2026年11月12日检索。每项后面的项目应用属于结合当前实现提出的方案，效果需要本项目实测。

### 1. 检索候选接口，动态加载工具

Anthropic的Tool Search按需发现并加载工具定义。ToolLLM研究也使用神经API检索器为请求推荐工具。[Tool Search官方说明](https://www.anthropic.com/research/advanced-tool-use) [ToolLLM论文](https://arxiv.org/abs/2307.16789)

应用到本项目，可保留完整Skill库，先按需求与当前待办检索少量相关接口，再由规划器选择。若首次检索不足，允许追加检索。需要同时记录全库规模、每轮可见候选数、检索召回、最终正确率与tokens，并与当前全接口曝光配置单独比较。

### 2. 外部存储与历史压缩

Anthropic的上下文工程说明采用轻量引用、按需读取、对话压缩和结构化笔记管理长任务状态。[上下文工程官方说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

项目已有DOC/FILE存储、产物回执和按需正文读取。进一步可以把历史压缩为原始目标、当前最终引用、未解决错误及剩余预算，完整历史继续保留在磁盘。压缩前后应检查原始事实、失败和终稿引用是否遗漏。

### 3. 独立核查具体断言，再定向修订

Chain-of-Verification先产生草稿，再提出验证问题，独立回答验证问题，最后生成经过核验的结果。[CoVe论文](https://arxiv.org/abs/2309.11495)

项目应用可以要求审查器逐条输出“文件与行号、实际断言、对应facts字段、支持状态”。如“无固定公网地址”必须能对应支持该断言的输入。命令、CSV和引用交给确定性程序检查，语义断言继续由独立内容复核判断。审查应读取原始facts与实际材料，避免只依赖生成物中的自我检查声明。

### 4. 用显式状态组织生成、审查与修订

LangGraph官方文档给出了orchestrator-worker以及evaluator-optimizer流程，后者通过评价反馈驱动重新生成。[LangGraph流程模式](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

项目已有审查反馈循环。进一步可显式登记“当前终稿集合、待修错误、错误对应引用”，每次修订后检查最终清单是否替换旧版本，再决定继续审查或提交。该设计直接针对旧错误附件仍留在交付集合的问题。

### 5. 扩大上下文并控制推理资源

KV缓存策略可在显存、速度和长上下文之间作取舍，量化与卸载是相关工程方法。[Hugging Face缓存文档](https://huggingface.co/docs/transformers/main/kv_cache)

本项目已有32k/40k对照，也使用q8_0 KV缓存。后续扩容应测实际峰值显存、延迟、输入输出tokens和最终正确率。更大容量可容纳更长请求，内容质量仍需按原标准核查。

### 6. 分开衡量调用正确与任务完成

BFCL的多步骤评估检查工具执行后的系统状态，并结合响应检查评价任务完成情况。[BFCL多轮评估说明](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html)

项目可继续分别记录接口是否合法、调用是否实际执行、文件是否正确、业务六标准是否满足，以及整个任务是否最终成功。这样能定位检索、规划、执行、审查和版本管理各环节的变化。

### 录制时可以采用的研究结论

已经实现并可展示的改进包括事实来源约束、稳定不可变引用、完整上游传递、回执与按需读取、真实审查反馈及实文件复核。工具检索、历史压缩、断言来源绑定和更严格的修订状态管理属于后续可测试方法。已有资料提供方法依据，本项目的收益由后续对照测量确定。
