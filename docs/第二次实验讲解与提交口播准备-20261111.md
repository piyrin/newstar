## 一、先理解一个真实成功例子

给模型的任务是为虚构开源项目 CourseDock 制作发布材料。输入给出了版本、功能、限制、两条命令和 CSV 字段，也明确保留了未知信息。

例如，输入给出了 `python -m coursedock serve --port 4177`，模型应原样保留这条命令。`default_port` 和 `web_management_ui` 都是未知，因此材料仍须保留这两项未知。

本地 F32 的 N166、seed3 实际走出了以下路径。

```text

  ↓ 生成 DOC-001 和实际 CSV 文件
```

这次 N=166、K=2、业务节点=2、最长链=2 个节点。DAG 来自实际调用及引用记录。模型在这次运行中选择了两个不同 Skill，并形成真实依赖。

## 二、Why —— 为什么设计这个实验

### 1. 要回答的研究问题

随着可用 Skill 增加，模型能否根据一段完整自然语言需求，选对能力、传递真实产物、完成可核查的结果？出现失败时，要找到选择、执行、事实约束、修订或上下文中的具体位置。

候选库增加，会增加接口描述开销和选择负担。执行后，上游材料、反馈与历史继续增长。因而实验同时记录完整任务成功情况和资源失败证据。

### 2. 为什么采用 CourseDock 材料任务

它同时包含说明写作、给定命令保留、真实 CSV 文件生成、建议流程设计和跨文档一致性，适合观察多 Skill 组合。

固定 facts 能让错误定位到具体句子。例如，将未知的 Web 界面写成确定不存在，就是可以对照输入核查的问题。使用虚构项目也便于冻结事实和公开演示。

本次验收覆盖发布材料生成。两条 CourseDock 命令作为输入事实检查，材料实验没有提供 CourseDock 软件实现的运行验收。

### 3. 为什么要测十次

单次运行容易受模型采样和执行路线影响。按老师要求，每个最终汇报配置完成十次完整任务，分母保留所有已完成的预定试次，包括上下文失败与未解决歧义。

本地使用固定 seed1～10。云端十次为十个独立完整运行，没有设置 API seed。两组均沿用一份完整业务任务，因此结论适用于当前任务与配置。

## 四、How —— 方案怎样实现

### 第一步，固定 Skill 身份和调用接口

每个来源保存原 `SKILL.md`、来源版本和 SHA256，注册为一个业务函数。统一参数为 `request` 和 `artifact_ids`，前者表达子任务，后者声明真实上游引用。

当前执行适配主要覆盖原文驱动的文本与文档任务。第三方账号、外部服务和原作者脚本的接通情况，需要各自的执行证据。

### 第二步，让规划器选择和组合

规划器同时看到 N 个候选的名称、说明和函数 schema，以及完整需求和 facts。具体 Skill、子任务与依赖由模型逐轮选择。

模型选中某个 Skill 后，执行器才把该 Skill 的完整原文、全部 facts 和实际引用的上游完整正文交给执行模型。这个加载方式是本轮实验配置的一部分。

主要入口见 `experiments/skill_boundary_f/progressive.py` 中的 `make_tools` 和 `run_one`。

### 第三步，把产物和依赖落到实处

输出正文保存为实际 Markdown 文件，CSV 代码块导出为实际附件。产物获得不可变 DOC/FILE 引用，修订产生新引用。

下游通过引用取得上游正文，程序同时记录生产节点、父节点、文件路径和哈希。这样可以核查模型究竟读取了哪份材料，并据实际引用还原 DAG。

相关实现见 `reference_store.py`。规划器通常取得长度、哈希和引用等回执，需要正文时调用 `read_artifacts`。业务执行和审查取得相关完整正文。

### 第四步，在同一预算内审阅和修订

每次最多 16 轮规划。模型完成初稿后调用 `review_deliverables`，错误反馈实际进入后续规划请求。模型可选 Skill 修订，重新审阅，再调用 `submit_deliverables` 提交通过审阅的同一引用集合。

读取、审阅和修订都使用这 16 轮预算。错误草稿和旧引用保存在证据中，最终清单明确列出交付对象。

### 第五步，多层核验

程序检查文件存在、引用、哈希、给定命令、CSV 字段顺序及空记录。语义审查结合原 facts 判断内容，全部自动正例再阅读全文并直接检查实际附件，另外保存独立复核记录。

冻结的六项内容标准为功能/限制/版本/许可准确、两条命令准确、实际空 CSV 正确、未知保持未知、流程与职责标为可用建议、最终材料一致。

独立复核属于本项目内的另一轮审查，教师验收仍待课程提交后进行。

### 第六步，保存可复查和可重跑的证据

冻结输入、来源和实现，保存每次请求、响应、依赖图、最终文件及评分记录。结果计数绑定具体审查记录和哈希。

已知 166/seed3 在新目录和便携环境中完成过正确功能重跑，重跑文字存在变化。包内离线校验验证文件完整性，完整推理重跑验证业务功能，两类结果分别记录。

## 五、失败原因与可以改进的方案

### 1. 已定位的上下文压力

166 档首个本地规划请求约有 28,781 个 prompt tokens，后续历史与反馈继续占用 32,768 上下文。三次实际输入分别达到 33,582、33,241 和 32,849 tokens 后报错。32,849-token 原请求又两次得到相同超限结果。

32k/40k 对照中，同一 33,582-token 请求在 40k 可继续，后续 41,226-token 请求又超限。扩大上下文可以容纳该请求，最终任务质量仍需检查实际内容。

### 2. 已定位的事实错误

模型会把来源作者当成项目负责人，或补造未知的界面、默认值、网络行为、数据收集保证。较小候选规模也出现过这些错误。

DeepSeek 第七次的“不提供 Web 管理界面”存在歧义，输入里的管理界面状态为未知。这项歧义保留了原文与裁定。

### 3. 已实现的改进

- 在完整 Skill 后加入事实来源边界，说明 Skill 作者及示例的适用范围，要求未知字段保持未知。
- 使用稳定的 `artifact://` 逻辑引用，减少不同磁盘运行目录造成的输入变化。
- 用产物回执控制规划历史增长，按需读取正文，同时向业务执行与审查提供完整相关正文。
- 将真实审查反馈送回规划器，并保存全部原始评分与后续复核。

上述实现已有运行与回归证据。各项改动对总体正确率的独立贡献尚待单因素对照。

### 4. 理论上可以继续改进的方向

以下属于依据本次失败提出的设计方案，预期收益需要新实验测量。

| 方向 | 解决的问题与实现方式 | 验证办法及代价 |
| --- | --- | --- |
| 分层检索与动态候选集 | 全库保留 166 项或更多，每轮检索少量相关接口，必要时扩展候选，降低接口描述占用 | 同任务对照全曝光与检索曝光，记录检索召回、最终正确率和 tokens。须同时报告全库 N 与每轮可见候选数，漏检会造成新失败 |
| 结构化事实及来源绑定 | 为确定事实附上 facts 字段引用，把建议单列，未知字段使用显式状态。生成后检查关键断言是否有依据 | 使用界面、默认值和数据行为等已知失败例回归，再加入新任务。仍需语义复核以处理改写与歧义 |
| 分阶段管理规划历史 | 保留目标、当前最终引用、待解决问题和有依据的状态摘要，完整原文继续落盘并按需读取 | 记录压缩前后上下文占用、遗漏问题及正确率。摘要丢失约束或失败信息会降低效果 |
| 独立审查与定向修订 | 审查输出具体文件、句子、输入依据和最小修订目标，让后续 Skill 聚焦处理错误 | 在固定预算下比较误收、误拒、总请求数和最终正确率。额外审查会增加成本，也可能引入评审偏差 |
| 多任务与受控模型对照 | 增加代码、数据处理等需要不同组合的任务，固定候选加载、审查、预算等条件再比较模型 | 每个条件预先登记重复次数，报告完整分母和不确定性。当前云端与本地模型、上下文和自动审查均有差异，后续可逐项控制 |

其中，检索与历史管理直接针对上下文开销，事实绑定与定向修订针对内容错误。新方案应单独编号并重新测量，与本轮冻结结果并列报告。
