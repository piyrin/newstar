# Skill 严格逐级扩容记录

日期：2026-11-09（北京时间）。按用户“不能通过不算”“逐渐往大扩展”的要求，改为每档全部通过才晋级。

## 当前结论

**改进配置下，本轮完整通过到10个候选Skill。15个这一档为5/6，未通过，已停止，未创建20个及更大规模的测试。**

这不是“模型硬上限为10”。它只表示当前模型、工具集合、发布材料任务族与六次验收定义下，已完整通过到10，下一档尚未完整通过。不能把15个的五次成功计为通过15，也不把过去163个的成功个例混入本轮结论。

## 冻结的任务和规则

- 项目发布材料一个任务族，使用CourseDock、LabLedger、ClubArchive三个虚构资料变体，每个重复两次，每档6次。
- 每次都要完成全部发布材料：准确的功能/限制说明、给定命令的新手说明、精确字段顺序的空CSV反馈模板，以及标为建议的反馈流转/维护职责。
- 5→10→15→20→…；同一档6/6完整通过后才调用下一档，缺失/重复试次、5/6、接口或资源错误均不能晋级。
- 候选集合嵌套，全部原始SKILL.md同时暴露为原生工具。模型自行选择工具、拆分任务和建立产物依赖，没有预设调用角色或DAG。
- 只验收最终清单中引用的真实最终版本，旧稿保留；最终答复不能补写未完成的交付。
- CSV实际落盘、解析并核对表头/空行；给定命令逐字核对；独立请求只核查六项业务要求，未知项允许保留。
- 任务实际使用至少两种Skill，且至少有一个节点读取上游产物，才算本组合基准通过。

这轮不与此前四类社团需求的比例混算，也不称为所有产品任务都已稳定通过。

### 初始组A的失败

10级的LabLedger第1次没有提交最终清单，耗尽16轮规划预算，实际产生19次调用、15节点最长依赖链。

原因可追踪：A011自行增加REVIEW.md，A015又增加INDEX.md，随后A016—A019为了这些自增材料反复同步文件清单和相互引用，超出用户原始交付需求。不能据此说“第10个Skill不可用”或“10是数量硬上限”。

证据：`tmp/skill-boundary-v2/incremental/gradual-20261109-a/n010/ledger-r1/`中的`dag.json`及最后三轮`planner-*.response.json`。

### 独立改进组B

仅给规划器增加通用终止约束：做满足原始需求的最小完整交付；不自增非必要索引/审阅文档；不为措辞、版本号、重复列出自身等反复修订；需求已满足就提交清单。

不提供标准答案、不指定工具、不提高16轮预算、不放宽验收，另开系列从5重新运行。原先失败的LabLedger第1次在B组10级用8次调用完成并通过验收。A组失败仍保留为失败。

判定器另加了“六项布尔值全真但errors非空也不能通过”的一致性保护。复核发现本次所有实际通过记录的errors本来都为空，这项加固没有改变任何既有结果。

### B组15级的失败

LabLedger第1次最终清单引用`A003-1`作为产物ID，但运行器实际登记的ID为`A003`。真实文件`A003-1.csv`确实已经生成，它是A003的附加导出文件名，不是另一个已登记产物ID。

因此不是“没有CSV文件”，而是**最终交付引用不合法，无法按接口选出完整交付**。本次整体失败，不能因为文件存在或其余五次通过就把15级计为通过。此次没有自动模糊匹配、替换ID或重抽一次补成6/6。

证据：`tmp/skill-boundary-v2/incremental/gradual-20261109-b/n015/ledger-r1/manifest.json`、`summary.json`和`artifacts/A003.json`。
