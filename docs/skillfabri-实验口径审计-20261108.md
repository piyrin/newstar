# 实验口径审计与作业重新对齐

用户指出老师实验室约100多个Skill，而此前结果达到2048，要求重新核对截图。核对对象为当前执行代码与实际落盘证据。老师的模型、框架及Skill加载方式未知；不推测其具体设置。

## 结论纠正

前面的实验把困难的“根据自然语言需求选择并组合Skill”，弱化为“为已拆好的8个角色寻找对应文档”。2048是候选目录规模，2207是文档注册数；它们不能证明同等条件下突破老师实验室的编排上限。此前作此暗示不成立，已在两份旧报告顶部标明纠正。

截图的核心要求是：逐步增加可调用Skill，系统按自然语言需求选择与组合，探索难以继续正确编排的位置；说明成功标准、多轮结果、失败位置与改进，并提供本人同步口播录屏。它没有规定每轮必须调用全部N个Skill，也没有规定必须使用函数调用或必须一次加载全部文档。

## 原始运行证据复核

审计结果保存于 `tmp/skillfabri-spike/scale/methodology-audit.json`：

- 12次scale-b完整流程的DAG内容哈希只有 **1种**。
- 12次输入brief内容哈希只有 **1种**。
- 每次均选择 **8种**，DAG均为 **10节点**。
- 所有12次合计实际完成调用的不同ID只有 **11种**。

11种包括原8种，以及customer-research、jobs-to-be-done-analyst、product-design-harness。其余注册文档没有在本轮证明原能力可运行。单次调用8种本身不违反截图要求；问题是没有把实际可调用规模和自主编排能力证明出来。

## 对齐后的实验协议建议

1. **定义“可调用”。** 逐个验证Skill入口、输入输出、依赖与最小功能用例。文档数、注册数、依赖缺失数、最小用例通过数分别统计。写作型与工具型Skill保留各自适当执行方式，不能全部退化成泛化写作提示词。
2. **让系统承担选择与组合。** 用户只给业务需求、输入和约束；不把标准子任务清单、固定8个角色、标准顺序交给规划模型。可让规划器产生Skill、参数、产物引用和依赖，执行器只检查合法性并调度。自动生成DAG是本方案的设计选择，不冒称截图的额外强制要求。
3. **保持第一轮环境与加载规则一致。** 记录模型、提示词、Skill暴露方式、检索/按需加载、重试和上下文预算。先测未经优化的基线，改进作为独立对照，不能将不同环境的数字直接比较。按需加载本身不违反截图，但此前未确认可比条件就据此外推不当。
4. **冻结任务与验收。** 准备需要不同组合的自然语言任务；包括相近描述、同名参数不同语义、单位/格式不同等可解释干扰。任务需求保持可独立判断对错，成功要求最终产物、事实与约束、关键中间结果及实际调用记录共同通过。增加Skill做多实验时保持每项业务任务难度可比；不要同时随意增加DAG深度而混淆原因。
5. **逐级逼近边界。** 可先按20/40/60/80/100/120/140/160/200个已验证Skill推进，每级多任务多次运行，在首次明显退化附近加密。100多个是老师结果提供的参照区间，不能预设为正确答案，也不能人为制造该阈值。
6. **分开报告规模。** 每次记录可调用库N、实际使用不同Skill数K、调用次数、有效DAG节点数、最长依赖链、完整任务成功率、首个失败位置及重试情况。稳定运行率分母包含预定的全部尝试，不能只计成功跑完的运行。
7. **录屏展示真实产品任务。** 若沿用竞赛题材，应实际处理通知、解析日期与条件、产生可用待办等业务产物；现有“竞赛管家”的多数结果只是产品方案、故事和测试文档。其文档链不能直接冒称完整竞赛管家已经实现。
