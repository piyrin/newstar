## 边界与原因对照

扩容器`boundary_scan.py`接受独立冻结registry，验证旧前缀完全一致、新增项目有匹配来源哈希的本地通过证据。每档至少2次，失败和未完成分别统计；边界档再加密。成功仍须完成业务全验收，不能把一次合法工具响应算作任务通过。

`context_replay.py`对保存的失败请求做全量新推理：messages、tools、采样、生成预算和模型保持逐字段一致，仅变更options.num_ctx。保存新响应和本地运行日志，检测输入裁剪/上下文移动/输出耗尽；不执行工具，不生成新业务成绩。

预备复现命令（目标目录必须为新目录）：

```powershell
python experiments/skill_boundary/boundary_scan.py --prefix 新边界系列 --registry tmp/skill-boundary-v2/local-qualification/boundary-expand-d/reviewed-registry.json --sizes 163 170 180 190 --repeats 3
python experiments/skill_boundary/context_replay.py --prefix 新上下文对照 --request tmp/skill-boundary-v2/progressive/local-single-confirm-163-a/n163/dock-r1/planner-04.request.json --contexts 32768 40960 --repeats 2
```

若真实通过的新增资格数量不足190，第一条命令会拒绝启动，不能补虚构条目；实际档位需根据已验证池确定。

## 已完成的相同输入对照与新发现

`context-controls/frozen163-context-a`是对旧163失败请求的4次全新推理。32k一次stop、一次length，40k两次stop；但是32k实测prompt为32640 token，40k同一输入为32906 token。随后`_debug_render_only`比较确认：默认32k输入长103972字符，禁止裁剪的完整输入长104683字符，哈希不同。旧日志中一次仍为truncated=0，说明仅检查底层日志不足以发现服务端先裁剪历史。

核对本机`/api/version`为0.33.1，并阅读[同版本官方routes.go](https://github.com/ollama/ollama/blob/v0.33.1/server/routes.go)和[api/types.go](https://github.com/ollama/ollama/blob/v0.33.1/api/types.go)：默认允许truncate/shift，渲染前可删除旧消息；原日志正则没有覆盖默认不输出的debug级别服务端裁剪信息。

修正后的`LocalAPI`明确发送`truncate:false, shift:false`。在独立对照`context-controls/frozen163-context-strict-a`内，保持消息、工具、模型、采样和5000生成token预算完全相同，只改变num_ctx：

| 上下文 | 两次结果 | 可支持结论 |
|---:|---|---|
| 32768 | 2/2明确HTTP400拒绝；请求32906 token超过窗口32768 | 该完整输入在此预算不可执行，不应静默裁剪为成功 |
| 40960 | 2/2正常stop；prompt均32906 token | 该完整输入可以推理返回；未执行后续工具，不能算业务通过 |

四次对照的除上下文外输入摘要均为`a3c6c7ab939fb2e0ae47472f10f481e365d579a0a7125774edad8865f72da9e8`。这是资源失败原因的重复证据，不是Skill数量硬上限。旧C组及两组复测正在逐请求比较默认渲染与完整渲染；完成前，其“全过程未裁剪”前提不再视为已证明，原业务产物/评分保留。

新增与原有离线回归共84项通过；它们只验证实现，不计真实模型试次。
